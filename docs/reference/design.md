# Design: Counterpart Ecosystem Monitor - Competitor Narrative Intelligence

## Problem Statement

The team currently has no systematic way to track competitors' public narrative content (blog posts, X/Twitter announcements, product updates). Information arrives via accidental discovery — someone happens to see a post while scrolling. This creates 1-2 day delays and persistent information anxiety: the team doesn't know what they don't know.

The existing codebase monitor solves a parallel problem for engineering activity (GitHub PRs). This project extends the Counterpart intelligence system from code activity to narrative activity.

## Demand Evidence

- **Primary signal:** Information anxiety. The team worries about missing competitor announcements but has no concrete incident where being late caused measurable damage.
- **Current state:** "目前团队内部获取信息的方式就是看大家刷到的时间，因此会有一定的滞后性，往往是在一两天之后才看到" — information flows through accidental browsing, not intentional tracking.
- **No loss event:** No specific case of "we were late and it cost us." This is a hygiene problem, not an emergency.
- **Demand category:** Product line completeness + information anxiety reduction. Not yet validated as a standalone need.

## Status Quo

Nothing. No RSS readers, no shared document, no assigned person, no systematic process. The "current solution" is random browsing. When the status quo is "nothing" and there's no concrete loss, that's a signal the problem may not be painful enough — but the product line extension argument (codebase + narrative = complete competitive intelligence) is the stronger justification.

## Target User & Narrowest Wedge

**First user:** The builder themselves. Dogfooding.

**Narrowest wedge:** A daily Lark card that summarizes what competitors published yesterday — blog posts and X posts — with LLM-generated analysis of significance and direction signals. If the builder reads it every morning for two weeks and finds it more reliable than random browsing, the product has value.

**Success metric (from Codex):** "Every morning I trust this report more than random browsing." Specifically: for 7 consecutive days, the builder reads the report and finds at least 3 items they would otherwise have missed or seen late.

## Constraints

1. Must integrate with existing Lark delivery (team already reads codebase monitor reports there)
2. **Budget:** LLM cap $40/month (estimated spend $15-30/month). X API cost is separate and depends on tier selection (see X Strategy below). Total operating budget target: $50/month excluding X API.
3. Blog RSS availability varies by competitor — some use Medium (good RSS), some use custom sites (requires scraping fallback)
4. Must not require manual maintenance beyond initial competitor list configuration

## Premises

1. **Report-type product, not alert-type.** Daily digest to Lark. Data model includes `urgency` field to support future alert validation — if dogfooding reveals 3+ "I wish I'd seen this sooner" events in 2 weeks, add lightweight alerts for high-signal events (funding, product launches, pricing changes).
2. **Start with blog + X only.** Blog RSS is reliable; X has API (paid). Don't try to cover Product Hunt, news, etc. until these two are proven.
3. **Mirror the codebase monitor's architecture.** Same 4-stage pipeline (Collector -> Analyzer -> Report Generator -> Lark Dispatcher), same tech stack (Bun + SQLite + Vercel AI SDK), same report format.
4. **LLM analysis is the core value.** RSS aggregators already exist. The value is structured analysis: direction signals, product strategy extraction, narrative shift detection — not raw content aggregation.
5. **Dogfooding first.** The builder is user zero. If they don't read it daily, no one will.

## Cross-Model Perspective

Codex provided an independent cold read. Key findings:

- **Steelman:** "A lightweight narrative intelligence system that turns competitor blogs and X posts into a daily 'what changed, why it matters, what we should do' brief. It is not a feed reader; it is an anxiety-reduction product."
- **Key insight:** "The real problem is not analysis depth yet. It is replacing accidental discovery with a dependable habit."
- **Challenged premise:** The report-vs-alert binary is false. Default to daily digest, but track urgency for future alert validation. (Accepted — urgency field added to data model.)
- **48-hour prototype:** Aligns with Approach A. Bun + SQLite + RSS + X + LLM classifier + Lark card. Skip: dashboard, auth, vector DB, complex trend analysis.

## Approaches Considered

### Approach A: Mirror Architecture (Minimal Viable) -- CHOSEN

Copy the codebase monitor's verified architecture. Replace GitHub collector with Blog RSS + X collector. Replace diff analysis with content analysis. Two independent repos, independent deployment.

- **Effort:** S (human: ~1-2 days / CC: ~30 min)
- **Risk:** Low
- **Pros:** Architecture proven, independent deployment, massive code reuse
- **Cons:** Public code drift between repos, two separate Lark reports, refactoring needed if merging later

### Approach B: Unified Platform (Ideal Architecture)

Merge both monitors into one platform with pluggable collectors (GitHub/Blog/X), shared pipeline runner, unified daily report.

- **Effort:** M (human: ~3-5 days / CC: ~2 hr)
- **Risk:** Medium
- **Pros:** Unified view, lower maintenance, easy to extend
- **Cons:** Requires refactoring working code, higher complexity, shared failure domain

### Approach C: Narrative Intelligence Engine (Creative/Lateral)

Maintain per-competitor "narrative state" — current messaging, product direction, narrative tone. Report changes, not content. Narrative drift analysis.

- **Effort:** L (human: ~1-2 weeks / CC: ~4 hr)
- **Risk:** High
- **Pros:** Highest output value, narrative drift analysis unique to market
- **Cons:** Over-designed for unvalidated demand, high LLM cost, delayed dogfooding

## Recommended Approach

**Approach A: Mirror Architecture.** The demand signal is weak (information anxiety, no concrete loss), so validation speed matters more than architectural elegance. Copy the proven pipeline, start dogfooding in one day, use data from two weeks of dogfooding to decide whether to upgrade to B or C.

### Architecture

Reference implementation: `couterpart-codebase-ecosystem` (sister repo, same machine). Key files to mirror: `src/pipeline/runner.ts`, `src/pipeline/stages/*.ts`, `src/storage/db.ts`, `src/scheduler/`, `src/utils/`. LLM calls use Vercel AI SDK's `generateObject` with Zod schemas for structured output, matching the codebase monitor's pattern.

**Secrets:** API keys live in environment variables (`LLM_BASE_URL`, `LLM_API_KEY`, `LARK_WEBHOOK_URL`, future `X_API_KEY`), loaded from `.env` file. A `.env.template` documents all required variables.

### Data Model

```sql
-- Tracked competitors
CREATE TABLE competitors (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    org TEXT NOT NULL,           -- organization slug
    blog_rss_url TEXT,           -- RSS feed URL (nullable)
    x_handle TEXT,               -- X/Twitter handle (nullable)
    website_url TEXT,            -- main website
    tags TEXT,                   -- JSON array of tags
    last_synced_at TEXT,         -- ISO timestamp
    created_at TEXT DEFAULT (datetime('now'))
);

-- Collected content items
-- X-related source type ('x_post') is defined now to avoid schema migration later,
-- but the X collector is not part of v1 scope (xEnabled: false).
CREATE TABLE content_items (
    id INTEGER PRIMARY KEY,
    competitor_id INTEGER NOT NULL REFERENCES competitors(id),
    source TEXT NOT NULL,        -- 'blog' | 'x_post'
    source_url TEXT NOT NULL,    -- canonical URL
    title TEXT,                  -- blog title or null for tweets
    content TEXT,                -- full text content
    content_hash TEXT,           -- dedup hash
    published_at TEXT,           -- original publish time
    collected_at TEXT DEFAULT (datetime('now')),
    analysis_status TEXT DEFAULT 'pending',  -- pending | complete | failed
    UNIQUE(source_url)
);

-- LLM analysis results
CREATE TABLE analyses (
    id INTEGER PRIMARY KEY,
    content_item_id INTEGER NOT NULL REFERENCES content_items(id),
    summary TEXT NOT NULL,       -- 1-2 sentence summary
    technical_detail TEXT,       -- deeper analysis
    category TEXT,               -- product_launch | strategy_shift | hiring | partnership | technical | marketing | other
    direction_signal TEXT,       -- what this reveals about competitor direction
    significance TEXT NOT NULL,  -- routine | notable | directional_shift
    urgency TEXT DEFAULT 'normal',  -- normal | high (for future alert validation)
    sentiment TEXT,              -- positive | neutral | negative | aggressive
    why_we_care TEXT,            -- one sentence on why this matters to us
    input_tokens INTEGER,
    output_tokens INTEGER,
    model_id TEXT,
    estimated_cost_usd REAL,
    analyzed_at TEXT DEFAULT (datetime('now'))
);

-- Analysis inputs (audit trail)
CREATE TABLE analysis_inputs (
    id INTEGER PRIMARY KEY,
    analysis_id INTEGER NOT NULL REFERENCES analyses(id),
    prompt_version TEXT,
    input_quality TEXT,          -- full | truncated | metadata_only
    competitor_context TEXT,     -- rendered competitor context
    raw_content_snapshot TEXT,   -- content at analysis time
    created_at TEXT DEFAULT (datetime('now'))
);

-- Generated reports
CREATE TABLE reports (
    id INTEGER PRIMARY KEY,
    report_date TEXT NOT NULL,
    report_type TEXT NOT NULL,   -- daily | weekly
    content TEXT NOT NULL,       -- JSON report payload
    item_count INTEGER,
    notable_count INTEGER,
    is_partial INTEGER DEFAULT 0,
    created_at TEXT DEFAULT (datetime('now')),
    UNIQUE(report_date, report_type)
);

-- Per-card Lark delivery tracking
CREATE TABLE report_deliveries (
    id INTEGER PRIMARY KEY,
    report_id INTEGER NOT NULL REFERENCES reports(id),
    card_content TEXT NOT NULL,
    delivery_status TEXT DEFAULT 'pending',  -- pending | sent | failed
    message_id TEXT,
    sent_at TEXT,
    error TEXT,
    created_at TEXT DEFAULT (datetime('now'))
);
```

### Collector Details

**Blog RSS:**
- Use a standard RSS/Atom parser (e.g., `rss-parser` or built-in XML parsing)
- Store full article text from RSS `content:encoded` or `description`
- **Content extraction fallback (required for v1):** If RSS content is truncated (under 500 characters), fetch the full page URL and extract article body using a readability algorithm (e.g., `@mozilla/readability` or `@extractus/article-extractor`). This is not optional — many competitor blogs serve truncated RSS.
- Dedup by canonical URL hash

**Pre-implementation RSS validation:** Before building, manually verify RSS feed quality for each target competitor. For each feed, check: (a) feed exists and returns valid XML, (b) content includes full article text or at least substantial excerpts, (c) feed updates within 24 hours of publication. Document results in `competitors.json` with a `rss_quality` field (`full` | `truncated` | `title_only` | `none`).

**RSS validation failure path:** If fewer than 2 of the 5 target competitors have usable RSS feeds (`full` or `truncated`), pause and re-evaluate whether a generic web scraping collector (using readability extraction on competitor blog index pages) should replace the RSS collector as the primary approach.

**Content extraction error handling:** If full-page extraction fails (paywall, JS-rendered, 403), store the truncated RSS content and set `input_quality = 'truncated'` in `analysis_inputs`. Analyze with what's available rather than skipping.

**X/Twitter Strategy:**

Launch v1 with blog RSS only. Run X collector evaluation as a parallel investigation track:
1. Evaluate X API Basic tier ($100/month) — likely too expensive for dogfooding validation
2. Evaluate self-hosted RSS-Bridge for X — free but relies on scraping, may break
3. Evaluate direct scraping — legally risky, technically fragile
4. If no viable X solution exists under $20/month, accept blog-only as v1 scope and revisit when/if X API pricing changes or a reliable bridge emerges

When X collector is ready:
- Store tweet text, media descriptions, quote tweet context
- Filter: only original tweets and quote tweets (skip replies, retweets-without-comment)

## Failure Modes

1. **Individual source fetch failure:** Skip the failing source, continue with others. Mark the report as `is_partial = 1`. Log the error.
2. **LLM API failure:** Retry with exponential backoff (3 attempts, 5s/15s/45s). If all retries fail, skip analysis for that item, mark `analysis_status = 'failed'`. Do not block the pipeline.
3. **Lark webhook failure:** Retry 3 times with 10s intervals. If all fail, log error and mark `delivery_status = 'failed'`. Failed deliveries are retried on the next pipeline run.
4. **Full pipeline failure:** Log error to `data/health.json`. Do not send an empty report. If 3 consecutive runs all fail, send a health alert to Lark.

## Schema Migration

Use SQLite `user_version` pragma for version tracking. On startup, `db.ts` checks the current `user_version` and applies numbered migration functions sequentially. Same pattern as the codebase monitor's `src/storage/db.ts`.

## Open Questions

1. **Language:** Competitor content may be in English or Chinese. LLM analysis and report output should be in Chinese (matching codebase monitor).
2. **Dedup across sources:** A competitor may announce the same thing on blog and X. Should we dedup or analyze both? (Recommendation: analyze both, but link them in the report.)
3. **Alert validation process:** How to systematically track "I wish I'd seen this sooner" events during dogfooding. (Consider: a simple CLI command `bun run mark-urgent <id>` or Lark card reaction.)

4. LLM cost stays within $40/month budget
5. After 2 weeks: decision on whether to continue, upgrade to Approach B/C, or discontinue
